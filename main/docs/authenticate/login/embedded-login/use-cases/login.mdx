## What is embedded login?

Embedded Login allows you to authenticate existing users directly within your application interface without redirecting to an external login page. You collect user credentials (or credentials are collected via passkey, email OTP, or SMS OTP), send them directly to Auth0's authentication API, and receive tokens in return — all without leaving your app.

This approach is ideal when you need complete control over the authentication experience, want seamless in-app flows, or must comply with policies that restrict external redirects.

## When to choose embedded login

Choose embedded login when:

- **UX demands it**: Your product requires a native or fully custom login experience that cannot be achieved with redirects.
- **No-redirect requirement**: You need to authenticate users mid-conversation (AI agents), during checkout, or in other contexts where redirecting would break user flow.
- **Native mobile apps**: You're building iOS or Android apps and want passkey enrollment, OTP entry, or other native experiences.
- **Restricted network policies**: Your users' networks or organizations prevent redirects to external login pages.
- **Custom validation or profiling**: You need to collect additional data or validate custom business logic before or after authentication.

Consider [Universal Login](/docs/authenticate/login/auth0-universal-login) instead if you prefer faster time-to-market, automatic security updates, and Auth0-hosted UI maintenance.

## Real-world scenarios

**Banking apps**: Mobile banking apps must maintain a branded, seamless login experience within the app. Embedded login enables this while maintaining security via DPoP token binding and biometric factors.

**Enterprise SaaS**: Corporate applications may have policies restricting redirects. Embedded login keeps the entire experience within the app environment.

**Conversational AI agents**: AI agents can authenticate users mid-conversation without breaking context. Users provide credentials or complete MFA challenges directly in the chat interface.

**E-commerce checkout**: Online stores can inline a login flow during checkout, letting users authenticate without leaving the purchase funnel.

**Kiosk applications**: Self-service kiosks can embed login directly in their custom interface for efficient user authentication.

## How embedded login works

<Steps>
<Step title="User initiates login">
Your app displays a login form or passkey selector within your native UI.
</Step>

<Step title="App collects credentials">
Gather the user's credentials directly in your app. What you collect depends on the grant type:
- **Resource Owner Password**: username and password
- **Passwordless**: email or phone number
- **Native Passkeys**: passkey assertion from the device
- **Native Social Login**: platform-native token from Google, Apple, or Facebook sign-in
</Step>

<Step title="App calls /oauth/token">
Your backend or frontend sends the credentials to Auth0's `/oauth/token` endpoint with the appropriate grant type.

<Tabs>
<Tab title="Resource Owner Password">
```bash
curl --request POST 'https://YOUR_AUTH0_DOMAIN/oauth/token' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=password' \
  --data-urlencode 'username=user@example.com' \
  --data-urlencode 'password=SecurePassword123!' \
  --data-urlencode 'client_id=YOUR_CLIENT_ID' \
  --data-urlencode 'client_secret=YOUR_CLIENT_SECRET' \
  --data-urlencode 'audience=YOUR_API_IDENTIFIER' \
  --data-urlencode 'scope=openid profile email'
```
</Tab>

<Tab title="Passwordless (Email/SMS OTP)">
```bash
# Step 1: Send OTP to user
curl --request POST 'https://YOUR_AUTH0_DOMAIN/passwordless/start' \
  --header 'Content-Type: application/json' \
  --data '{
    "client_id": "YOUR_CLIENT_ID",
    "client_secret": "YOUR_CLIENT_SECRET",
    "connection": "email",
    "send": "code",
    "email": "user@example.com"
  }'

# Step 2: Exchange OTP for tokens
curl --request POST 'https://YOUR_AUTH0_DOMAIN/oauth/token' \
  --header 'Content-Type: application/json' \
  --data '{
    "client_id": "YOUR_CLIENT_ID",
    "client_secret": "YOUR_CLIENT_SECRET",
    "grant_type": "http://auth0.com/oauth/grant-type/passwordless/otp",
    "username": "user@example.com",
    "otp": "123456",
    "realm": "email",
    "audience": "YOUR_API_IDENTIFIER",
    "scope": "openid profile email"
  }'
```
</Tab>

<Tab title="Native Passkeys">
```bash
# Step 1: Request passkey challenge
curl --request POST 'https://YOUR_AUTH0_DOMAIN/passkey/challenge' \
  --header 'Content-Type: application/json' \
  --data '{
    "client_id": "YOUR_CLIENT_ID"
  }'

# Step 2: Exchange passkey assertion for tokens
curl --request POST 'https://YOUR_AUTH0_DOMAIN/oauth/token' \
  --header 'Content-Type: application/json' \
  --data '{
    "grant_type": "urn:okta:params:oauth:grant-type:webauthn",
    "client_id": "YOUR_CLIENT_ID",
    "auth_session": "<session_id_from_challenge>",
    "authn_response": "<authenticator_assertion_response>",
    "audience": "YOUR_API_IDENTIFIER",
    "scope": "openid profile email"
  }'
```
</Tab>

<Tab title="Native Social Login">
```bash
# User authenticates with platform-native social sign-in
# (Google Sign In, Sign In with Apple, Facebook Login)
# Your app receives an id_token or authorization code from the provider

# Exchange the provider token for Auth0 tokens
curl --request POST 'https://YOUR_AUTH0_DOMAIN/oauth/token' \
  --header 'Content-Type: application/json' \
  --data '{
    "grant_type": "urn:ietf:params:oauth:grant-type:token-exchange",
    "client_id": "YOUR_CLIENT_ID",
    "subject_token": "<id_token_or_auth_code_from_provider>",
    "subject_token_type": "http://auth0.com/oauth/token-type/apple-authz-code",
    "audience": "YOUR_API_IDENTIFIER",
    "scope": "openid profile email"
  }'
```

<Note>
The `subject_token_type` varies by provider. Use `http://auth0.com/oauth/token-type/apple-authz-code` for Apple or the appropriate token type for Google and Facebook.
</Note>
</Tab>
</Tabs>
</Step>

<Step title="Auth0 validates and returns tokens">
Auth0 verifies the credentials, checks MFA requirements, and returns access tokens, ID tokens, and refresh tokens.
</Step>

<Step title="App uses tokens">
Your app stores the tokens and uses the access token to call your API resources on behalf of the user.
</Step>
</Steps>

## Supported authentication methods

Embedded login can be powered by several authentication methods:

### Resource Owner Password Grant (ROPG)

For applications with database connections or social IdP logins where you collect and submit credentials directly:

- [Resource Owner Password Flow](/docs/get-started/authentication-and-authorization-flow/resource-owner-password-flow) — detailed flow documentation
- [Call Your API Using ROPG](/docs/get-started/authentication-and-authorization-flow/resource-owner-password-flow/call-your-api-using-resource-owner-password-flow) — implementation guide

### Passwordless (Email/SMS OTP)

For login flows using one-time passwords:

- [Embedded Passwordless Login](/docs/authenticate/passwordless/implement-login/embedded-login) — email and SMS OTP flows
- [Auth0.js signup and login methods](/docs/libraries/auth0js) — JavaScript SDK for web apps

### Native Passkeys

For iOS and Android apps, you can use platform-native passkey APIs for frictionless, phishing-resistant authentication:

- [Native Passkey Enrollment](/docs/authenticate/passwordless/implement-login/embedded-login/native-passkeys) — on-device passkey setup for iOS/Android

### Native Social Login

For native mobile apps, let users authenticate with platform-native social sign-in (Google, Apple, Facebook) without opening a browser. Your app uses the platform SDK to get a token from the social provider, then exchanges it with Auth0 via token exchange:

- [Add Sign In with Google to Native Android Apps](/docs/authenticate/identity-providers/social-identity-providers/google-native)
- [Add Sign In with Apple to Native iOS Apps](/docs/authenticate/identity-providers/social-identity-providers/apple-native)
- [Add Facebook Login to Native Apps](/docs/authenticate/identity-providers/social-identity-providers/facebook-native)

### Lock SDK & Auth0.js

Pre-built UI components that embed login directly in your web app:

- [Lock for Web](/docs/libraries/lock) — customizable login widget
- [Auth0.js](/docs/libraries/auth0js) — minimal JavaScript SDK for custom UI

## Important security considerations

### First-party SSO with custom domain

If you want users logging into your embedded flow to share SSO sessions with your other applications, you must use a [custom domain](/docs/customize/custom-domains). This enables first-party cookie behavior and seamless SSO across your apps.

Without a custom domain, SSO will not work because requests to Auth0's default domain (`*.auth0.com`) are treated as third-party.

### DPoP token binding (Native apps)

For native mobile and desktop applications, consider implementing [Demonstrating Proof of Possession (DPoP)](/docs/secure/tokens/access-tokens/token-binding/demonstrate-proof-of-possession) to bind tokens to the device and prevent token theft.

### Session management with refresh tokens

Use refresh tokens as lightweight session artifacts to avoid full re-authentication during step-up flows or when tokens expire.

For applications that call multiple APIs, use a [Multi-Resource Refresh Token (MRRT)](/docs/secure/tokens/refresh-tokens/multi-resource-refresh-token) to obtain access tokens for different API audiences from a single refresh token. This eliminates the need for separate authentication flows per API — your app authenticates once and uses the MRRT to get scoped access tokens for each resource as needed.

See [Refresh Tokens](/docs/secure/tokens/refresh-tokens) for details.
